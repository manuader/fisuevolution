# E12 — Ranking de la llegada a Dios: nombre moderado, Supabase y la pestaña · plan de implementación

> **Para agentes:** SUB-SKILL OBLIGATORIA: `superpowers:subagent-driven-development`
> (recomendada) o `superpowers:executing-plans`, tarea por tarea. Los pasos usan checkbox
> (`- [ ]`). Cada tarea con oráculo corre además el bucle del harness AVO (journal del run en
> `FisuEvolution/.claude/avo/2026-10-06-fisu-v2/journal.md`, en el checkout principal).

**Goal:** que la 2.0 tenga un ranking global de quién llegó a Dios y cuánto tardó: el tiempo real
lo pone el reloj del servidor, el tiempo jugado lo mide el teléfono y sólo se muestra, el nombre
pasa por las mismas reglas en la app y en el servidor (manda el servidor) y después por una lista
de palabras y por Claude Haiku. El jugador lo vive en una tarjeta al llegar a Dios y en una
pestaña "Ranking" del menú deslizable, con su fila siempre visible, "Mis partidas", "Reportar" y
el gancho a la Tienda.

**Architecture:** tres capas que se construyen por separado y se juntan al final.

- **El backend** vive en `supabase/` (directorio propio, fuera de `FisuEvolution/` y de
  `project.yml`): migraciones SQL versionadas (tablas, RLS, la vista `leaderboard`, funciones SQL
  atómicas), cuatro Edge Functions finas (`start-run`, `finish-run`, `leaderboard`, `report`) más
  `remoderate` para el cron, y una carpeta `_shared/` con la lógica pura (reglas del nombre,
  lista de palabras, moderación con Haiku inyectable). Se prueba entero en local: Deno + un
  Postgres temporal, sin proyecto de Supabase.
- **Lo puro de la app** vive en EconomyKit: `NameRules` (la misma tabla de casos que el servidor,
  leída del mismo JSON) y `RankingState` (la máquina de estados de la partida rankeada, su
  migración, su regla de conflicto y lo que sobrevive al reset).
- **La app** suma `Managers/Ranking/` (`RankingClient` protocolo + HTTP + simulado,
  `InstallIdentity` en el Keychain, `RankingConfig` local + remota, `RankingStore` observable) y
  `UI/Ranking/` (la tarjeta de Dios y la pestaña). `GameState` sólo engancha cuatro momentos:
  el cierre del núcleo del tutorial, el reset, la vuelta/salida de `.active` y el reveal de Dios (más una línea en `GameState.swift` para guardar la referencia al store).

**Tech Stack:** Swift 6 (strict concurrency `complete`, warnings como errores) · SwiftUI ·
EconomyKit (SPM puro, `Sendable`) · Swift Testing · XCUITest · XcodeGen · Supabase (Postgres 15+,
Edge Functions en Deno 2) · `npm:postgres` (driver con consultas parametrizadas) ·
`npm:@anthropic-ai/sdk` (Haiku) · `Tools/v2/catalogo.py`.

**Fuente:** `Docs/superpowers/specs/2026-10-08-v2-e12-ranking-design.md` (las decisiones del
dueño de ese documento son **cerradas: no se re-litigan**), `Docs/PLAN-v2.md` E12, §0/§0.1
(relevo y agentes concurrentes), §2 (decisiones) y §4 (orden), `tasks.md` §1, §3, §5 (E1, E3a,
E3b, E9b, E2b, E10, E12) y §6, y las trampas de `Docs/HANDOFF.md` §2 y §7. Lo que el código
contradice o el spec deja abierto está en "Para el dueño / dudas", con un default que no frena.

**Rama de la épica:** `v2/e12-ranking`, desde `version-2`. Cada tarea sale de su punta en un
worktree propio (`worktrees.nosync/v2i-e12-t<n>`, rama `v2i/e12-t<n>`: el

## Global Constraints

- `SWIFT_TREAT_WARNINGS_AS_ERRORS: YES` y `SWIFT_STRICT_CONCURRENCY: complete`. **Nada de
  `Timer`** para la lógica: los reintentos del ranking se disparan al volver a `.active` y al
  terminar una llamada, nunca por reloj.
- **El `.xcodeproj` no se versiona**: `/opt/homebrew/bin/xcodegen generate` al agregar o borrar
  un archivo Swift o un JSON de `Resources/Config`, en el mismo paso. `supabase/` no está en
  `project.yml` y no se agrega.
- **Strings nuevos, es + en, siempre por `Tools/v2/catalogo.py`** (trampa 29). Cada tarea
  escribe `Tools/v2/claves-pendientes/e12-tN.json`; si en su ola es dueña de
  `Localizable.xcstrings` lo aplica y commitea el catálogo, si no commitea sólo el JSON y el
  controlador lo aplica al integrar. Todas las claves bajo `ranking.*`. Los números se
  interpolan (`%1$@`), nunca se escriben a mano; un `Int` interpolado va como `String`
  (trampa 5).
- **El nombre del jugador se muestra SIEMPRE con `Text(verbatim:)`**: nunca `Text(LocalizedStringKey)`,
  `AttributedString(markdown:)`, `WebView` ni interpolación en una clave. Tampoco entra en un
  `String(format:)` como formato (sólo como argumento).
- **Nada de secretos en el repo.** `ANTHROPIC_API_KEY` y la `service_role` viven sólo como
  secretos de Supabase. La URL del proyecto y la clave anónima son públicas por diseño (viajan en
  cada `.app` y RLS es la protección): van en `Resources/Config/ranking.json` recién en T16, con
  el OK del dueño (duda 4). Hasta entonces el JSON trae `null` y la app usa el cliente simulado.
- **Nunca red real bajo XCTest ni bajo `--uitest*`**: `RankingStore.isLive` (patrón
  `NotificationsManager.isLive`) elige `SimulatedRankingClient`. Los UI tests eligen escenario
  con `--uitest-ranking-<escenario>`.
- **El servidor escribe sólo con consultas parametrizadas**: las Edge Functions llaman funciones
  SQL con el tagged template de `npm:postgres` (`sql\`select … ${valor}\``), jamás
  `sql.unsafe` ni concatenación. Un test de Deno lo vigila (grep de `unsafe(` en `functions/`).
- **RLS prendido en todas las tablas**; `anon`/`authenticated` no tienen `INSERT/UPDATE/DELETE`
  en nada ni `EXECUTE` en ninguna función; sólo `SELECT` sobre la vista `leaderboard`. Lo
  verifica un test SQL.
- **`accessibilityIdentifier` en cada control nuevo, nunca en un contenedor con hijos**
  (trampa 9a-bis). Prefijo `ranking.`.
- **FisuJobs es la referencia visual** (`PanelCard`/`GameCard`, `ActionPill`, `StateBadge`,
  `GameConfirmCard`, paleta y tipografía de la casa). Nada de alertas ni botones del sistema.
  Toda hoja con `fisuSheet()`.
- **EconomyKit no conoce UI, `Bundle`, red ni `Date()`**: recibe el `now`.
- **El estado del ranking vive en `meta.ranking`** (`RankingState`, save v6) con
  `decodeIfPresent ?? .legacy` y su regla en `SaveConflictResolver`: **no se sube el schema**.
  Trampa E7a: todo lo que se persiste lleva su `init(from:)`.
- **"Partida" no es `RunState`.** En el código de la app, la partida rankeada es
  `RankingState`/`rankedGame`, que abarca todas las reencarnaciones desde el núcleo del tutorial
  (o el reset) hasta Dios. `runId` es el id del servidor (tabla `runs`), y se documenta así en el
  tipo para que nadie lo confunda con `player.run`.
- Código limpio y con pocos comentarios. **Commits en español, estilo
  `feat(ranking): …` / `test(ranking): …` / `feat(backend): …`, SIN `Co-Authored-By`.** Staging
  selectivo por archivo y `git diff --cached --stat` antes de cada commit.
- **Al cerrar cada tarea** (lo hace el controlador): integración + `Docs/SESION-<fecha>-v2-e12.md`
  + las cuatro ediciones de `Docs/HANDOFF.md` + journal y `LOCK`. Ningún subagente toca `Docs/`,
  `handoffs/`, `tasks.md`, el journal ni `Tools/v2/rojos-declarados.txt`.

## El flujo, de punta a punta

```
partida nueva (núcleo del tutorial)  ─┐
reset confirmado (E9b T8)            ─┴─► RankingState.awaitingStart ──► start-run (con red; si no, en cada .active)
                                                                        │ servidor: started_at = now()
                                                                        ▼
                         RankingState.running(runId, serverStartedAt, playedSeconds += cada sesión .active)
                                                                        │ markRevealed(tier tope)
                                                                        ▼
                  RankingState.reachedGod(stamp pendiente) ──► finish-run SIN nombre (sella finished_at ya)
                                                                        │ servidor: real_seconds = finished − started
                                                                        │           < piso → status review
                                                                        ▼
         tarjeta "¡Llegaste a Dios en 32 h 14 min!" (primer momento calmo)
             ├─ "Entrar al ranking" → finish-run con nombre (misma partida, tiempos fijos)
             │      reglas → lista → Haiku ──► ok · pending (Haiku caído → "Anónimo", cron 15 min) · rejected (pedir otro)
             └─ "Ahora no" → queda pendiente; se completa desde la pestaña
```

- **El sello no espera al nombre** (duda 2): el `finish-run` sin nombre sale apenas se llega a
  Dios, así "Ahora no", escribir despacio o un rechazo no le suman horas al jugador. Sin red, el
  sello sale en la primera vuelta a `.active` con red: el corte juega en contra, nunca a favor.
- Una partida con `name_status = missing` (sellada sin nombre) **no se publica**.

## Contrato HTTP (lo cumplen el servidor y `HTTPRankingClient`)

Todas `POST` con cuerpo JSON (nada en la URL: regla de privacidad), headers
`Authorization: Bearer <anon>` y `apikey: <anon>` (el gateway de Supabase los pide), `Content-Type:
application/json`. `installId` es el UUID en minúsculas; el servidor guarda
`sha256(installId)` en hex.

| Función | Cuerpo | 200 |
|---|---|---|
| `start-run` | `{installId, appVersion, clientRunId}` (`clientRunId`: UUID que el cliente genera una vez por partida nueva o reset; el mismo id devuelve la misma partida sin abandonar nada) | `{runId, startedAt}` (epoch s, del servidor) |
| `finish-run` | `{installId, runId, playedSeconds, name?}` | `{status: "finished"\|"review", nameStatus: "ok"\|"pending"\|"rejected"\|"missing", realSeconds, rank?}` |
| `leaderboard` | `{installId, mine?: bool}` | `{top: [Row], me: Row?, myRank?, mine?: [MyRun], fetchedAt}`; `Row = {runId, rank, name?, realSeconds, playedSeconds, isMe}` (`name` `null` = "Anónimo") |
| `report` | `{installId, runId}` | `{ok: true}` (idempotente) |

`MyRun` (en `mine`, de `leaderboard` con `mine: true`) = `{runId, startedAt, finishedAt?, realSeconds?, playedSeconds?, name?, nameStatus: "ok"|"pending"|"rejected"|"missing", status: "finished"|"review"}`; las fechas son epoch s enteros y los opcionales vienen `null` si no hay dato; orden: la más reciente primero. `Row.rank` y `myRank` son enteros.

Errores: `400 {error:"invalid"}` (cuerpo o nombre inválido por reglas), `403 {error:"not_owner"}`,
`409 {error:"not_active"}`, `429 {error:"rate_limited"}`, `503 {error:"disabled"}` (el interruptor
del servidor, `settings.ranking_enabled`), `500`. El cliente trata 5xx, timeout y sin red como
"reintentar"; 4xx como definitivo (salvo 429: reintentar en la próxima vuelta).

**Objetivo:** la regla del nombre, pura, con **una sola tabla de casos** que leen Swift y Deno.
Puede ir ya.

**Files:**

- Create: `Packages/EconomyKit/Sources/EconomyKit/Ranking/NameRules.swift`
- Create: `Packages/EconomyKit/Tests/EconomyKitTests/NameRulesTests.swift`

**Interfaces:**
- Produces: `public enum NameRules` con `static let maxLength = 15`,
  `static func validate(_ raw: String) -> Result<String, NameRules.Rejection>` (devuelve el
  normalizado), `static func filterTyping(_ raw: String) -> String` (lo que deja escribir el
  campo), `static func isAllowed(_ scalar: Unicode.Scalar) -> Bool`;
  `public enum Rejection: String, Error, Sendable { case empty, tooLong = "too_long", forbidden }`.
- La regla, en este orden (el mismo en `name_rules.ts`):
  1. NFC (`precomposedStringWithCanonicalMapping`);
  2. cualquier escalar fuera de lo permitido → `forbidden` (antes que el largo: `Robert'); DROP
     TABLE` es `forbidden`, no `too_long`);
  3. recortar espacios de los bordes y colapsar los internos a uno;
  4. vacío → `empty`; más de 15 caracteres → `too_long`.
- **Permitidos**: `A–Z`, `a–z`, `0–9` (sólo ASCII), espacio U+0020, `.`, `-`, `_`, y las letras
  latinas precompuestas: U+00C0–U+00D6, U+00D8–U+00F6, U+00F8–U+024F (Latin-1, Extended-A y -B)
  y U+1E00–U+1EFF (Latin Extended Additional). Nada más: ni marcas combinantes sueltas (una
  `e`+U+0301 se compone en NFC y pasa; una que no compone, no), ni cirílico, ni dígitos no ASCII,
  ni anchos completos, ni `×`/`÷`. Con sólo precompuestos, **un escalar = un grafema**: el conteo
  coincide en Swift (`count`) y en JS (`[...s].length`).
- `filterTyping`: NFC, saca los escalares no permitidos, colapsa espacios dobles (no recorta los
  bordes: el jugador puede estar por escribir la segunda palabra) y corta en 15.

create table public.players (

-- La mejor partida publicada de cada jugador. "Anónimo" (name = null) si el nombre está
-- pendiente o la partida juntó 3+ reportes. Se publican sólo finished con nombre ok o pending.
create view public.leaderboard with (security_invoker = false) as
with eligible as (
  select r.*, (select count(*) from public.reports p where p.run_id = r.id) as report_count
  from public.runs r
  where r.status = 'finished' and r.name_status in ('ok', 'pending')
), best as (
  select distinct on (player_id) * from eligible
  order by player_id, real_seconds, finished_at
)

       player_id,
       case when name_status = 'ok'
             and report_count < (select (value)::int from public.settings where key = 'reports_to_hide')
            then name end as display_name,
       real_seconds, played_seconds, finished_at,
       rank() over (order by real_seconds, finished_at) as rank
from best;

export function haikuClassifier(apiKey: string): Classifier {

  return async (name, signal) => {
    try {
      const msg = await client.messages.create({
        model: "claude-haiku-5-5",
        max_tokens: 64,
        system: SYSTEM,
        output_config: {
          effort: "low",
          format: { type: "json_schema", schema: {
            type: "object", properties: { ok: { type: "boolean" } },
            required: ["ok"], additionalProperties: false } },
        },
        messages: [{ role: "user", content: `Nombre: ${JSON.stringify(name)}` }],
      }, { signal });
      if (msg.stop_reason === "refusal") return "unavailable";

   cachea un CDN. Default: caché de 60 s en memoria de la función (el top) y en la app (no
